# 从框架现象到可复现缺陷

## 先提出可检验假设

“兑换偶尔失败”不意味着 Spring 或数据库有 bug。先记录输入、事务边界、精确版本和并发条件，判断是业务规则、使用方式、环境差异、文档缺口还是实现缺陷。

把观察与解释分开：日志证明发生了什么，官方契约说明预期是什么，最小复现帮助确定哪些因素是必要条件。

## 缩小复现

移除与触发无关的服务和真实数据，使用固定依赖、合成输入和一条可执行命令。逐步改变一个变量，例如版本或配置，避免同时升级所有依赖后无法解释结果。

复现成功仍需核对支持范围；若本来就使用了未支持的 API 或组合，应该修正用法。已有上游 Issue 可提供线索，但必须确认触发条件相同。

## 规避与升级

workaround 只覆盖已知条件，引用问题编号并记录移除标准。过宽的兼容补丁会掩盖新错误，永久 fork 会增加长期维护成本。

上游合并修复后，等待包含修复的实际发布版本，并在最小复现和 Magic 场景上回归。不要仅凭 Issue 关闭就删除规避代码。

## 对外反馈与学习资产

本地形成可审阅的 Issue 草稿，获得明确授权后再发送；私人数据、令牌和未披露安全细节不进入公开报告。没有确认或反馈链接时保持真实状态。

Magic 将复现、原因和结论保存在 [上游台账](../upstream/README.md)，长期保留能帮助后续维护的知识。当前尚无业务框架缺陷记录，不使用虚构案例填充台账。

具体规则与模板见 [缺陷流程](../dev-rules/upstream-bugs.md)和 [记录模板](../templates/upstream-bug.md)。

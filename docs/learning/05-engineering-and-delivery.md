# Monorepo、交付与可观测性

## 一个仓库不等于一种构建工具

Monorepo 将跨服务契约、客户端和运行手册放在同一次变更中，便于比较和学习。Java、Go、Python、Rust 和 Dart 仍使用原生工具；pnpm 管理 Node 生态，后续 Taskfile 负责统一任务入口。

先用明确的任务依赖和必要检查，规模增长后再评估 Nx 等增量编排。缓存键必须包含锁文件、工具链、配置和生成输入，错误缓存比慢构建更难诊断。

## 文档本身也是工程

M0 用 markdownlint 检查格式，用 markdown-it 和 github-slugger 校验链接与锚点，用 YAML 解析器核对工作流配置。项目专属脚本管理文档登记及门禁连接，不重新编写 Markdown 语法解析器。

检查工具也可能出错，因此要验证断链、缺失登记、错配检查名和不安全配置等反例。通过表示规定的检查成功，不表示语义一定正确或业务已验收。

M0 的实际接入发现：pnpm 12 的锁文件可以包含多个 YAML 文档，检查器需解析全部文档，同时保留重复键等错误检测；markdownlint 的模块入口和 CLI 入口不同，必须用失败样本证明工具真的执行了检查。这些是本项目接入经验，不是上游 bug。

## 一个阶段一个提交

阶段内部连续实现和修复，最终提交描述完整结果。未推送修复可以 amend；推送后的共享历史默认保留，再通过 PR squash 保持 main 的阶段粒度。这样的组织需要清晰的阶段范围与报告，不能用大提交掩盖无关工作。

GitHub 的授权边界与技术门禁不同：检查成功仍需用户批准 push、PR 或合并；用户批准操作也不自动说明检查通过。

## 一键部署的检验

未来的一键部署应能在文档规定的全新环境中启动，并在重复执行、配置缺失、迁移失败与恢复备份时保持可理解的行为。只证明容器启动不够，还要验证登录、发帖、兑换或对应阶段的实际流程。

待做实验：使用固定镜像部署，写入合成数据后升级并恢复；观察健康检查、日志与追踪能否定位失败。工具还未实现时只保留设计，不伪造演示结果。

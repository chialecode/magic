# 学习方法与选型证据

## 从一个问题开始

“学习消息队列”可以转化为“帖子获得奖励资格后，即使商城临时停机，也能最终发放积分且不重复”。这样便有明确输入、失败条件和可验证结果。

先记录用户场景和当前基线，再比较同步 API、数据库任务和 MQ。技术优势应由恢复、延迟、实现与运维成本共同解释，不能只用吞吐宣传决定。

## 选型记录的五个部分

1. 目标：解决哪个用例、学习哪个机制、哪些内容不在本次范围。
2. 候选：至少比较一个更简单方案，列出成熟开源实现及官方来源。
3. 证据：精确版本、维护和发行、支持平台、许可、重要限制及复查日期。
4. 实验：相同环境、可重建输入、成功和失败指标、最低可接受结果。
5. 结论：采用、调整、暂缓或归档，以及维护成本和退出方式。

## 如何判断来源

官方文档说明契约，仓库与发行说明帮助判断实现和修复，实际测试确认本项目环境中的行为。Star 数是社区关注信号，不能替代适配验证。

GitHub 的 `releases/latest` 不等于所有项目的官方稳定发行渠道。Flutter 在本次查询中返回旧预发布元数据，因此 SDK 必须按官方发行渠道核对。许可证识别返回 `NOASSERTION` 时，阅读实际许可文件，不能假设为 MIT。

## Magic 的实践入口

提案进入 Now／Next／Later；实验在独立目录；正式决策写 ADR；结论回到本手册。只有内容已实际运行时才标记实验通过。

建议第一个工程实验：从全新 checkout 安装锁定文档依赖并运行验证，然后故意制造断链，确认命令失败。M0 的脚本回归已采用这一思路，结果见阶段报告。

# 项目原则与已确认要求

本页记录方向及明确用户要求，具体实现由架构和 ADR 细化。原则可以通过后续明确决定修订，不将项目冻结在首次设计。

| 编号 | 已确认要求 | 来源 |
| --- | --- | --- |
| P-001 | 以型月世界观和二次元内容为主题，以开发者技术学习为主要目标 | 2026-10-07 项目定义 |
| P-002 | 代码规范，优先采用广泛使用、持续维护的开源实现 | 2026-10-07 项目定义 |
| P-003 | 覆盖论坛、资料站和站内数字内容商城，长期实践 Java、Go、Python、Rust、Vue、React、Flutter、小程序等技术 | 2026-10-07 项目定义 |
| P-004 | 使用 Monorepo，并最终提供脚本一键部署，充分利用 GitHub | 2026-10-07 项目定义 |
| P-005 | 后续允许从技术兴趣出发产生需求，需求和方案可持续变化 | 2026-10-07 长期演进要求 |
| P-006 | 首期商城使用演示积分，数字内容限站内使用 | 2026-10-07 商城边界确认 |
| P-007 | M0 以文档、详细架构、技术栈、开发规范与开发流程为主，并建立技术选型学习目录或 GitBook | 2026-10-07 M0 范围调整 |
| P-008 | 记录使用开源框架过程中发现的疑似或已确认 bug，形成可复现、可追踪的学习资产 | 2026-10-07 新增目标 |
| P-009 | 首个 commit 只包含空 README；之后一个阶段一个 commit；push 和 PR 需用户同意；远端设置分支保护 | 2026-10-07 Git 要求 |

不把技术覆盖面等同于首期全部部署。每种正式技术应承担实际业务、具备学习文档、质量检查和替换策略。

成熟开源能力优先用于认证、数据库、存储、监控与构建；社区规则、资料结构、积分权益和资源契约承载业务学习。发现上游问题时，先验证是否为使用或配置错误，再形成上游缺陷结论。

单机 Compose、具体框架、数据库和客户端划分是当前设计建议，详细状态见 [技术栈](../design/technology-stack.md)。M0 采用文档工具不表示提前批准所有未来产品依赖。

# ADR-0002：业务域与多语言主栈

日期：2026-10-07。状态：proposed，作为当前设计主选，尚未安装和验证产品框架。依据：P-002、P-003、P-005。

## 背景

项目需要长期覆盖多种后端和客户端技术，又需要可运行的业务闭环。随意拆分相同 CRUD 或将交易分散到多种语言会增加无学习收益的协调成本。

## 决定建议

以社区、资料、商城、资源四个边界承载 Go / Gin、Python / FastAPI、Java / Spring Boot、Rust / Axum；Vue / Nuxt 承载社区资料，React / Next.js 承载商城，Flutter 和 Taro 逐步接入多端。

各域拥有数据，关键交易留在本地事务，跨域使用明确 API 和可恢复事件。初期共用基础设施实例但隔离凭据，不继续拆分更细服务。

## 替代方案与取舍

单语言模块化应用最容易运维，但不能满足长期多语言实践目标。按技术随意切分服务可以快速覆盖语言，却会让业务规则分散。当前设计选择业务边界作为约束，接受一定多服务运行成本。

主框架有成熟替代方案，详细比较和官方来源见技术栈与学习手册。具体版本在进入实现时锁定；每种框架承担有意义功能后再计入技术覆盖。

复查条件：服务依赖出现循环、事务跨域难以保持、资源成本超出预算、框架维护或兼容性不再符合要求。

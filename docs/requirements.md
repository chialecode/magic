# Magic 需求与实施路线

版本：0.2 持续演进基线

日期：2026-10-07

状态：用于拆分 Issue 和编写架构决策记录；不是已实现功能清单。最新用户要求见 [项目原则](product/principles.md)，实际状态见 [执行状态](delivery/status.md)。技术细节由 [总体架构](design/architecture.md)、[技术栈](design/technology-stack.md)及专项设计维护，本页保留需求层面的摘要。

## 1. 项目定位与决策原则

Magic 是一个以型月世界观和二次元内容为主题的社区项目，也是一个以真实业务为载体、可持续演进的多技术栈学习工程。

项目成功应同时满足三个条件：用户能完成有意义的业务流程；开发者能说明技术选择及其取舍；新贡献者能复现开发、验证和部署过程。

| 层次 | 要求 |
| --- | --- |
| 用户已明确的目标 | 长期演进且需求可持续调整；论坛、商城、资料站；Java / Go / Python / Rust；Vue / React；Flutter / 小程序等主流客户端；Monorepo；脚本一键部署；优先成熟开源实现；充分使用 GitHub |
| 用户已确认的商城边界 | 学习演示，积分交易，数字藏品和内容仅限站内使用 |
| 用户已确认的 M0 与协作要求 | M0 以文档、架构、技术栈、学习手册及开发规范为主；记录开源框架 bug；首提交为空 README，阶段单提交，push 与 PR 经用户同意，远端启用保护 |
| 本稿的建议默认值 | 单机 Docker Compose 优先；Web 优先交付；各业务域内部先保持模块化；逐步覆盖多端 |
| 开发前仍需核实 | 首批内容及授权来源、仓库公开性、部署资源、客户端构建与签名条件、具体依赖版本 |

需求优先级：业务正确性与可复现性 → 学习价值与代码质量 → 技术覆盖面 → 规模化与性能优化。技术覆盖是整个项目的长期约束，首个里程碑不要求所有语言和客户端同时上线。

本稿是可修订的需求基线。功能表中的“必须”表示该能力一旦被纳入当前迭代后应满足的要求，不表示所有能力已经排期，也不表示未来不能修改。用户已确认的约束、建议默认值和待评估选项必须保持可区分。

“每种语言采用一个最流行框架”建议调整为“每种语言选定一个生态成熟、广泛使用、持续维护的主框架，并保留选择依据”。流行程度没有统一口径，也会变化；Star 数不能单独代表采用率、维护质量或安全性。

## 2. 命名与业务域

两套缩写可以同时成立：前者用于模块命名，后者用于解释内容范围，不必二选一。

| 模块 | 产品职责 | 主要数据归属 |
| --- | --- | --- |
| Magic | 门户、论坛、圈子与创作交流 | 社区资料、圈子、帖子、评论、关注关系、社区审核记录 |
| Akasha | 角色、作品、设定和世界线资料站 | 词条、实体关系、引用来源、修订历史、资料审核记录 |
| Grail | 积分商城、收藏和数字内容权益 | 积分账本、商品、库存、订单、权益、商城审核记录 |
| Imaginary | 数字内容处理、发布与分发 | 资源包、文件版本、资源清单、上传与处理任务 |
| Circuit | 公共工程与平台能力 | 身份接入、配置约定、可观测性、部署与交付工具 |

Circuit 是共享平台能力的集合，不要求单独建立一个包揽所有逻辑的服务。初期通知、举报、管理界面按所属业务域实现；只有出现实际复用需求才提取为公共服务。

主业务闭环：浏览资料 → 进入关联讨论 → 参与社区 → 获得演示积分 → 兑换数字内容 → 在帖子或客户端中使用 → 管理个人收藏。

## 3. 用户与权限

- 游客：浏览公开帖子、公开词条、商品介绍及合法公开预览。
- 注册用户：发帖、评论、收藏、关注、参与圈子、使用积分和个人数字内容。
- 资料贡献者：提交词条与修订；发布权限由资料审核规则决定。
- 创作者：提交资源包和商品资料；审核通过后才可上架。
- 版主与审核员：在授权范围内处理帖子、词条、资源和举报。
- 管理员：管理平台配置、角色和运营操作；敏感操作记录审计日志。

角色按业务域授权，并校验资源归属。例如某个圈子的版主不能因此修改全部词条或发放积分。世界观称号、等级和徽章属于展示体系，不能隐式获得管理权限。

身份系统维护登录凭据和稳定用户标识；业务服务维护自身用户资料及领域权限。统一身份服务优先采用成熟开源方案，例如 Keycloak，通过 OIDC 接入应用；GitHub 登录作为上游身份来源之一，并保留可用于本地演示的账号登录。

## 4. 功能需求与验收

### 4.1 论坛与圈子

首期必须具备分区、标签、发帖、编辑、评论、分页、收藏、个人主页、关键词检索和基础管理能力。圈子先提供加入、退出、角色管理与圈内发帖，实时聊天以后独立立项。

内容支持 Markdown、图片、关联词条和剧透标记；富文本输出必须清理危险内容。帖子编辑、删除、审核和举报需要明确状态及可见性。

验收：用户可发布并检索帖子；未授权用户不能编辑他人内容；被隐藏内容不得继续出现在列表与搜索结果中；管理员操作能够追溯。

### 4.2 Akasha 资料站

资料站提供作品、人物、组织、地点、能力、事件等结构化词条，以及标签、关联关系、时间线、来源引用、修订历史、差异比较和回滚。

型月相关资料需要明确“作品／版本／世界线／剧透等级”，允许区分原作事实、引用材料与社区解读。同名角色和不同世界线的差异不能简单覆盖成一个最终值。

导入任务必须支持进度、失败原因、重试和来源记录。自动抽取、向量检索和 RAG 是后续学习需求，资料站的阅读、编辑和搜索不得依赖外部模型服务。

验收：一次修订可以审核、发布、比较和回滚；词条可以关联讨论；搜索结果遵守内容可见性；导入失败不会留下无法辨识的半成品。

### 4.3 Grail 积分商城

首批商品包括表情包、头像框、个人主页装扮、站内主题及客户端可用的主题资源包。每个商品必须明确内容清单、支持客户端、资源版本、使用范围、是否限量与获取条件。

积分是演示用的站内记账单位，不充值、不提现、不兑换法币。积分获取由明确的演示任务或社区奖励规则驱动，配置频率限制和重复发放保护。首期不支持用户间转让、转售、拍卖和链上资产。

“数字藏品”定义为可展示的站内收藏记录和内容使用权，可以包含编号、获取时间与来源；不因此表示获得作品版权，也不承诺链上所有权或投资价值。

必须实现商品展示、上架与下架、库存、积分账本、订单、权益发放、个人收藏、兑换记录和运营退款／撤销流程。

- 积分使用整数最小单位，余额和流水必须可核对；修正通过冲正或补偿记录完成，不直接改写历史流水。
- 一次兑换在 Grail 本地事务中完成库存占用或扣减、积分扣减、订单落库和权益发放，不能靠前端连续调用来保障正确性。
- 订单和积分发放接口必须幂等。同一幂等键及相同请求重复提交返回同一结果；相同键对应不同请求应拒绝。
- 并发兑换不能导致库存或余额为负；奖励事件重复投递只能记账一次。
- 商品下架默认阻止新兑换，既有权益是否撤销必须由单独规则决定。退款、资源撤下和违规处置的影响需要分别定义。
- 首期使用同步完成的兑换流程；将来引入外部支付时再新增支付状态、支付回调、对账和超时关闭。

验收：余额不足不扣款；重复点击只产生一笔扣减与一次权益发放；并发争抢最后一件商品仅一人成功；失败可追踪；退款按规则恢复积分并撤销权益。

### 4.4 Imaginary 数字内容

负责上传、隔离检查、资源处理、版本化发布、预览和受控下载。资源包使用明确的清单格式，声明版本、兼容客户端、文件摘要、授权信息和内容类型。

首期主题采用声明式配置和静态资源；不接受任意脚本作为主题执行。上传需限制文件类型、体积、解压后大小及路径，避免将未审核文件直接公开。

商品及其使用权益由 Grail 管理；资源文件与版本由 Imaginary 管理。Imaginary 在受限内容下载前验证用户权益，不能将“知道文件 URL”视为已购买。

验收：已兑换用户可在论坛使用表情、在支持的客户端应用主题；无权益用户不能获得新的受限下载凭证；初期下载链接有效期建议不超过 5 分钟，权益撤销后不再签发新链接。已经下载到本地的普通文件不能保证被远程收回，离线缓存的处理规则应在产品中说明。

### 4.5 公共体验与运营

必须具有统一登录、返回原页面、个人中心、基础通知、错误反馈、加载与空状态、移动端适配、键盘可用性和深浅色设计规范。中文优先，并预留国际化资源结构。

后台提供内容审核、举报处理、账号限制、商品和资源管理、积分操作及审计查询。图片与文件有来源和授权记录，举报处理包含作品权利问题。开发演示使用原创、授权或可合法再使用的素材；代码许可证与内容使用许可分别管理。

## 5. 后端技术栈与边界

| 语言／主框架 | 业务分工 | 对应学习主题 | 原生工具建议 |
| --- | --- | --- | --- |
| Go + Gin | Magic 论坛与圈子 | API、分页、并发控制、缓存、后续实时通知 | Go modules、gofmt、go vet、golangci-lint；数据库采用 pgx，复杂 SQL 可配 sqlc |
| Python + FastAPI | Akasha 资料与导入 API | 类型化接口、数据建模、异步任务、检索与后续 AI | uv、Ruff、mypy、pytest、SQLAlchemy、Alembic |
| Java + Spring Boot | Grail 积分、商品、订单、权益 | 事务、幂等、领域建模、数据一致性和对账 | Java LTS、Gradle Wrapper、Spotless、JUnit、Flyway；持久层优先 Spring Data JPA |
| Rust + Axum | Imaginary 资源处理与分发 API | 内存安全、流式处理、异步 I/O、资源限制 | Cargo、rustfmt、Clippy、Tokio、SQLx |

四个框架是主选建议，不宣称其在所有口径下都排名第一。Rust 的 Axum 与 Actix Web 都值得比较，本稿选择 Axum 主要考虑 Tokio / Tower 生态。具体版本在服务建立时通过 ADR 锁定，并记录兼容性和升级方式。

数据归属与通信约束：

1. 本地可共用一个 PostgreSQL 实例，但各业务域使用独立数据库和凭据，只有所属服务能写入自己的数据。禁止跨服务直接联表和修改表。
2. API 优先 HTTP + JSON，以 OpenAPI 为契约；按需生成 TypeScript 和 Dart 客户端。gRPC、GraphQL 仅在存在具体学习需求与比较目标后引入。
3. 统一用户 ID、UTC 时间、分页、错误码、请求 ID、鉴权声明和兼容策略。可能超过 JavaScript 安全整数范围的 ID 在 JSON 中使用字符串。
4. 关键业务规则只在其所属服务实现。例如权益以 Grail 为准；客户端、论坛和资源服务不能各维护一套可独立变更的兑换规则。
5. 对需要可靠传递的跨域事件使用事务 Outbox 和幂等消费者。消息采用至少一次投递假设；必须定义重试、失败记录、人工重放、积压监测和版本兼容。
6. MQ 按可靠事件需求引入，建议 RabbitMQ；引入前也必须保证 Outbox 可恢复投递。队列和缓存不能替代权威账本。
7. 所有远程调用设置超时；仅对可安全重试的操作自动重试。资料导入或资源处理失败不应阻塞论坛基础阅读。

部署单元按业务域拆分，各服务内部从模块化实现开始。暂不继续拆成独立的积分、库存、订单、支付等小服务，以避免首期依赖分布式事务。

## 6. 多端技术与功能范围

| 客户端 | 推荐实现 | 主要职责 | 完成标准 |
| --- | --- | --- | --- |
| 社区与资料 Web | Vue + Nuxt + TypeScript | 论坛、圈子、资料阅读编辑及相应管理入口 | 响应式、SSR／SEO、权限与核心阅读写作流程 |
| 商城 Web | React + Next.js + TypeScript | 商品、兑换、收藏、主题预览及相应管理入口 | 与社区统一身份，兑换并使用权益的完整流程 |
| 移动客户端 | Flutter / Dart | Android 与 iOS 的浏览、发帖、通知、收藏和主题应用 | 分别构建、安装并在可用的目标设备验证 |
| 微信小程序 | Taro + React + TypeScript | 轻量阅读、搜索、圈子入口、个人收藏 | 在开发者工具及真机完成最小流程；上线能力再按平台规则配置 |
| 桌面客户端 | 优先复用 Flutter | Windows / macOS / Linux 的阅读、离线资料与主题管理 | 先验收 Windows，其他平台按真实构建和安装结果交付 |

Web 与客户端共享设计令牌、图标规范、API 契约和生成的 SDK；Vue、React、Flutter、小程序的界面不要求共享同一套组件代码。小程序不默认具备浏览器完整运行环境，登录回调、存储和下载需要单独适配。

首期管理入口可放在各应用的授权路由中；是否整合独立控制台以后决定。Electron、Tauri、React Native 和原生客户端可以成为专题实验，但不与同用途的正式客户端同时无限扩张。

Android、iOS、桌面系统和小程序需要各自的构建、签名或发布条件。服务端“一键部署”不等于应用商店和小程序平台自动审核通过；构建完成与正式发布分别验收。

## 7. 成熟开源实现优先

优先复用认证、数据库、反向代理、文件存储、编辑器、搜索、监控和构建工具；订单、积分权益、资料实体及社区规则作为学习主线自行实现。需要学习成熟产品时，可参考 Discourse、Wiki.js 等已有项目，并在复用代码前核实许可与技术匹配程度。

| 能力 | 建议选择 | 引入条件 |
| --- | --- | --- |
| 持久化 | PostgreSQL | 基础依赖 |
| 身份接入 | Keycloak / OIDC | 建立统一登录时引入 |
| 入口代理与 TLS | Caddy | 本地统一入口及单机部署 |
| 对象存储 | S3 兼容接口；本地候选 SeaweedFS | 需要附件与资源包时引入，核实具体 S3 API 兼容性 |
| 缓存与限流 | Valkey | 有明确缓存或分布式限流需求时引入 |
| 可靠消息 | RabbitMQ | 出现可靠跨域事件时引入 |
| 检索 | 首期 PostgreSQL；中文分词或相关性不足时评估 OpenSearch | 以中文检索用例实测决定，不将原生全文检索等同于完善中文搜索 |
| 可观测性 | OpenTelemetry、Prometheus、Grafana，按需加入 Loki / Tempo | 基础日志先行，完整套件放入可选部署配置 |

每个重要依赖的选型记录至少包含：用途、替代方案、许可证、最近发布与安全修复情况、维护活跃度、社区采用证据、文档与测试质量、迁移成本。开源许可证、云服务协议和免费额度不是同一件事。

## 8. Monorepo 与代码规范

以下是目标结构，不代表现在已创建这些应用：

```text
magic/
├── apps/
│   ├── community-web/       # Nuxt
│   ├── market-web/          # Next.js
│   ├── flutter-client/      # 移动端与桌面端
│   └── miniapp/             # Taro
├── services/
│   ├── magic/               # Go / Gin
│   ├── akasha/              # Python / FastAPI
│   ├── grail/               # Java / Spring Boot
│   └── imaginary/           # Rust / Axum
├── packages/                # 设计令牌、图标、生成的客户端 SDK
├── contracts/               # OpenAPI、事件 schema、资源包 schema
├── infra/                   # Compose、入口代理、监控；后续 Kubernetes
├── scripts/                 # 初始化、检查、迁移、部署、备份与恢复
├── docs/                    # 需求、ADR、运行手册、学习记录
├── experiments/             # 有边界、有结论的技术实验
└── .github/                 # 工作流、Issue 表单、PR 模板、CODEOWNERS
```

统一任务入口建议使用 Taskfile，JS 项目使用 pnpm workspace，其他语言保持原生构建和锁文件。Nx / Turborepo 等增量编排工具在项目规模需要时再评估，不强制它们管理所有语言工具链。

代码规范要求包括：格式化、静态检查、明确的模块边界、统一配置方式、公开 API 文档、数据库迁移、依赖锁定、错误处理和日志约定。每个服务必须有启动说明、依赖说明、健康检查和必要测试。

需要共享的是协议和开发约定，不是跨语言业务实现。公共目录不能成为循环依赖或任意工具函数的集合；生成代码应能通过任务命令重建，并检查生成结果是否过期。

## 9. 一键开发与部署

暂按 Linux 单机 Docker Compose 作为参考部署目标；Windows 开发通过 Docker Desktop / WSL2 支持。版本与最低系统要求应在实现阶段明确。

下列命令是未来脚本的验收接口，当前尚未实现：

```text
task doctor                     # 检查依赖、端口、配置和磁盘
task dev                        # 启动开发配置
task check                      # 格式、静态检查及相关测试
task deploy ENV=demo            # 部署固定版本并运行健康检查
task smoke                      # 检查核心业务链路
task backup                     # 导出数据库、资源及必要配置
task restore BACKUP=<path>      # 从指定备份恢复
```

“一键”指在文档列明的前置条件已满足后，一条命令完成配置校验、拉取或构建、启动依赖、执行迁移、加载演示数据和健康检查。演示数据只在 demo 环境启用；本地演示无需购买第三方服务或接入真实支付。

验收要求：

- 全新环境按文档完成前置准备后，可一条命令得到可登录、可操作的系统。
- 重复执行不会重置数据、重复创建商品或覆盖密钥；配置缺失时给出明确错误。
- 固定镜像 tag 或 digest，保存应用版本与迁移版本，不依赖漂移的 `latest`。
- 持久化数据库和对象文件；重启后数据保留；关键依赖未就绪时不能误报部署成功。
- 升级前能够备份，升级后执行冒烟验证；说明应用回滚和数据库恢复的区别，破坏性迁移不能仅通过回滚镜像解决。
- 初始管理员凭据随机生成并安全交付；数据库与对象存储管理端口不直接暴露公网；公网 TLS 需要域名等前置条件。
- 定期执行恢复演练，验证“备份文件存在”之外的实际可恢复性。

初步性能验收环境建议为 4 vCPU / 8 GiB 内存 / SSD 的 Linux 主机，完整监控套件可关闭。该配置是待实测的规划基线，不是已验证的最低资源承诺。Kubernetes / Helm 留给后续部署与扩缩容专题。

## 10. GitHub 协作与交付

| GitHub 能力 | 在 Magic 中的用途 |
| --- | --- |
| Issues + Issue Forms | 功能、缺陷、技术实验与选型提案，附业务价值和验收条件 |
| Projects + Milestones | 维护待办、进行中、评审、完成状态，以及按里程碑交付的范围 |
| Pull Requests + CODEOWNERS + Rulesets | 代码评审、检查门禁与目录责任归属；单人维护时采用可执行的规则 |
| Actions | 多语言检查、单元和集成测试、契约检查、镜像构建与部署 |
| GHCR | 服务镜像与不可变版本归档 |
| Releases | 版本说明、部署清单、客户端产物与升级注意事项 |
| Pages | 项目文档和学习记录；不承载需要后台运行的社区服务 |
| Discussions | 项目设计和开发交流；用户社区本身仍由 Magic 提供 |
| Dependabot + CodeQL | 支持范围内的依赖更新和代码扫描，其他语言／生态用相应工具补齐 |
| Environments + Secrets + OIDC | 环境隔离；支持 OIDC 的部署目标使用短期凭证 |
| Artifact attestations + SBOM | 记录构建来源和依赖清单，在适用套餐中接入验证 |
| Dev Containers / Codespaces | 为服务端与 Web 提供可复现环境，移动端构建仍需对应工具链 |

工作流要求：

1. PR 触发受影响项目的检查；共享契约、基础工具或工作流变更需要扩大检查范围。必需检查保持稳定的总入口，避免路径过滤使检查一直等待。
2. 合并后构建按 Git 提交标识的镜像；发布 tag 生成版本清单，记录各服务镜像和客户端兼容版本。
3. 部署演示环境后运行核心流程验证；若以后增加真实运营环境，单独定义发布与回滚策略。
4. 第三方 Actions 固定可信版本，优先完整提交 SHA；工作流权限最小化，来自 fork 的不可信代码不得获得发布密钥。
5. 对 Java、Go、Python、Rust、Node 和 Dart 分别设置依赖更新与检查策略，不能假设一种扫描工具覆盖全部生态。
6. 将 GitHub 套餐、仓库公开性、Actions 用量及平台构建成本纳入选型。高级扫描、私有仓库构建证明和部署保护等能力应核对当前可用范围。

GitHub 集成的交付结果不仅是几份 YAML，还应包括一次可追踪的“需求 → PR → 检查 → 发布 → 部署 → 验证”记录。

## 11. 非功能需求与完成定义

下面是建议的初始验收目标，需要在第一轮部署与压测后校准并记录实测条件：

| 维度 | 初始要求 |
| --- | --- |
| 正确性 | 积分、库存、订单和权益满足事务、幂等与并发约束 |
| 性能 | 在记录资源、数据量与缓存条件的环境中，50 个并发用户持续 10 分钟；核心列表／详情 API 的 p95 ≤ 500 ms，非预期服务错误率 < 1%；不包含文件传输和导入任务 |
| 故障恢复 | 应用进程重启不丢失已提交数据；后台任务可恢复；记录演示环境的恢复步骤与耗时 |
| 可观测性 | 结构化日志、请求／追踪 ID、健康检查、错误率、延迟、任务积压；不记录令牌等秘密 |
| API 兼容性 | 契约变更检查；客户端未同步升级时有明确兼容窗口与废弃流程 |
| 安全与权限 | 服务端鉴权、资源归属校验、上传限制、敏感日志脱敏和管理审计 |
| 易用性 | 核心页面适配移动屏幕，提供可理解的错误提示与键盘操作 |
| 可维护性 | 重要设计有 ADR；依赖可复现；每个服务有迁移、运行和故障处理说明 |

测试按风险分配：账本与订单状态转换采用单元和真实数据库集成测试；跨服务接口采用契约测试；核心闭环采用端到端测试；兑换额外验证并发与重复请求。不为简单展示代码追求机械的全量覆盖率。

一个需求完成，必须同时具备：明确用例和验收结果、符合规范的实现、相关自动检查通过、必要的失败路径验证、更新后的契约与文档，以及在目标演示环境中可复现的操作流程。文档应明确写出尚未测试的平台和限制。

## 12. 滚动路线与能力里程碑

以下里程碑描述可独立验收的能力及建议依赖顺序，不是固定排期。每轮仅承诺当前的少量需求；后续里程碑可以重排、缩小、合并或拆分。技术兴趣变化时可提前探索其他语言或客户端，但不能因此将实验依赖强加到已稳定的功能上。

| 里程碑 | 交付范围 | 核心验收 |
| --- | --- | --- |
| M0 文档与架构基础 | 详细架构、技术栈、技术学习手册、缺陷记录、开发与文档规范、GitHub 模板和文档检查 | 文档可导航、选型有证据、本地门禁可运行；远端接线按授权验证 |
| M1 社区可用 | Go / Gin、Vue / Nuxt、论坛、基础圈子、登录、审核、搜索 | 登录 → 发帖 → 评论 → 搜索 → 审核；一键部署 |
| M2 资料可用 | Python / FastAPI、词条、修订、引用、导入、论坛关联 | 编辑 → 审核 → 发布 → 回滚 → 关联讨论 |
| M3 商城闭环 | Java / Spring Boot、Rust / Axum、React / Next.js、积分、订单、权益、资源分发 | 获得积分 → 兑换 → 获得权益 → 在社区使用；至此覆盖四种后端语言和两种 Web 框架 |
| M4 移动与小程序 | Flutter Android / iOS、Taro 微信小程序、统一登录与核心 API | 在实际可用平台上验证阅读、互动、收藏和资源使用；标明各端范围 |
| M5 桌面与工程深化 | Flutter 桌面、备份恢复演练、完整可观测性、发布证明与兼容管理 | 可安装客户端、可追踪发布、可复现恢复与性能报告 |
| M6 持续技术专题 | AI 检索、图谱、实时通信、Kubernetes、WebAssembly 等 | 每个专题有独立需求、对比、指标与去留结论 |

不为缺少人员规模和投入时间的计划编造工期。每个里程碑交付后系统都应可用，并能独立演示；下一个里程碑不能迫使已完成的基础功能长期失效。

GitHub Projects 使用滚动规划区分三类需求：

- **Now：** 当前承诺，建议每位开发者最多一到两个进行中的事项；有可执行的验收条件和清晰的范围。
- **Next：** 近期候选，业务目的明确，技术细节和交付顺序可调整。
- **Later：** 长期方向与技术兴趣池，不承诺交付时间，也不要求提前做完整设计。

当前 Now 为 M0 文档与架构基础，真实样例应用、Compose 和最小论坛移至 M1。其余先放入 Next 或 Later；不把整个 M0 到 M6 同时列为进行中。阶段验收正本见 [路线与验收](delivery/roadmap-and-acceptance.md)。

## 13. 以技术为切入点的持续需求机制

允许“先想学习某项技术，再寻找应用场景”，但每次进入主项目都必须回答：谁受益、改善哪条流程、为什么当前实现不够、如何测量、维护成本是什么、失败后如何退出。

统一流程：技术兴趣 → 场景假设 → Issue → 选型 ADR → 有边界的实验 → 指标评估 → 合并或归档。实验在 `experiments/` 中进行，成熟后才成为正式部署依赖。

| 技术主题 | 可应用的需求 | 评估方式 |
| --- | --- | --- |
| WebSocket | 评论或圈子消息实时提醒 | 重连、离线补偿、通知延迟 |
| 向量检索 / RAG | 带引用的设定问答 | 引用可核验性、检索命中率、无依据回答比例 |
| 图数据库 | 角色、组织和世界线关系探索 | 与关系数据库实现比较查询复杂度和运维成本 |
| WebAssembly | 浏览器端资源预览和格式校验 | 延迟、下载体积和内存，相比现有实现的收益 |
| Kubernetes | 服务故障恢复和受控扩缩容 | 部署复杂度、恢复时间与资源成本 |
| 测试网 NFT | 学习钱包与凭证验证的独立实验 | 签名校验、链上链下一致性；不改变已确认的首期商城范围 |

使用 [技术学习需求模板](templates/technology-proposal.md) 记录提案。学习成果允许是“这种技术不适合当前场景”，不以增加一个常驻服务作为必然成功标准。

### 开源框架缺陷也是学习目标

使用开源框架时，记录疑似与已确认缺陷、精确版本、最小复现、调查过程、临时规避和升级回归。区分本项目使用问题、文档缺口与上游实现缺陷，不以数量作为目标。

统一入口为 [技术学习手册](learning/README.md)和 [上游缺陷台账](upstream/README.md)，执行 [缺陷流程](dev-rules/upstream-bugs.md)。对外发送 Issue、评论或 PR 需要明确授权；记录目标本身不授权公开发送。

## 14. 长期演进与需求变更

### 14.1 分层管理，避免需求文档变成不可修改的合同

| 层级 | 内容 | 调整方式 |
| --- | --- | --- |
| 项目原则 | 学习导向、真实业务、成熟开源、多技术栈、Monorepo、可复现交付 | 低频调整；在文档中说明项目方向为何变化 |
| 产品与架构基线 | 业务域、用户流程、权限、数据归属、API 兼容规则、正式技术栈 | 根据实践修订；影响多个业务域时记录设计与迁移决策 |
| 当前迭代 | 具体用例、验收条件、缺陷、重构和实验 | 通过 Issues / Projects 高频调整，每个交付点复盘 |

框架、存储、中间件和客户端方案可以替换。可演进性的主要保障是清晰的数据归属、稳定的边界契约、可重建的环境和可验证的迁移，不是提前为所有组件设计抽象层。

### 14.2 变更按影响处理

- 文案、界面和局部实现调整：在 Issue 或 PR 说明变化，同步相关验收与文档即可。
- 功能范围或业务规则调整：说明旧行为、新行为、原因、受影响用户及新的验收条件。例如积分规则变化应明确是否影响历史积分。
- 跨服务、接口、数据模型或正式技术栈调整：使用简短的变更提案及 ADR，记录替代方案、迁移步骤、兼容窗口、回退方法和验证结果。
- 紧急缺陷：先修复并验证，随后补齐记录，不让文档流程阻碍必要处理。

单人维护不要求为每个改动建立正式评审会议。文档复杂度与变更风险相匹配；跨边界的重要决定必须能被未来的自己理解。

### 14.3 明确当前事实与历史依据

`docs/requirements.md` 维护当前有效的需求；GitHub Issues / Projects 维护执行状态；ADR 保存重要决策及其替代关系；Releases 和运行手册描述实际已发布的行为。不要在多处各维护一份容易冲突的待办清单。

需求可使用 Proposed、Accepted、In progress、Done、Deferred、Dropped 等状态；旧需求被替代时链接到新需求，并写明取消或替代原因。重要需求保留稳定编号，例如 `GRAIL-001`，关联 Issue、PR 和验证记录。

不得因为新设计已写入文档，就将迁移或功能标记为完成。计划、实验、当前实现与已发布行为需要明确区分。

### 14.4 允许替换，保留恢复能力

数据库变更优先采用“先兼容扩展 → 迁移数据与调用方 → 验证 → 再移除旧字段”的方式。已安装的移动端无法保证同时升级，破坏性 API 变更必须定义兼容窗口或明确的版本支持策略。

改变积分或权益规则前说明历史数据处理方法；替换框架或服务前验证迁移、回归与回退；实验默认独立或通过功能开关启用，并设置评估和清理条件。无需永久保留每一种旧技术，完成替换后应移除失效代码和依赖。

每次小版本交付后回顾：哪些需求仍有价值、哪些实现过度、哪些依赖需要升级、哪些实验可以结束。长期积累的技术债与依赖维护应作为正式任务进入计划。

使用 [需求变更模板](templates/change-proposal.md) 处理重要调整；技术学习驱动的新功能继续使用技术提案模板，必要时相互链接。

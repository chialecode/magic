# 路线与验收

路线采用滚动规划，M0 范围已按用户最新要求调整为文档与架构基础。后续能力顺序可以变更，不能把未来候选误记为当前必须交付。

## 1. 里程碑

| 里程碑 | 范围 | 核心结果 |
| --- | --- | --- |
| M0 | 文档治理、架构、技术栈、学习手册、上游缺陷流程、开发规范和文档门禁 | 可审阅、可导航、可验证的工程与设计基础 |
| M1 | Go / Gin、Vue / Nuxt、统一登录、最小论坛、真实 Compose 部署 | 登录、发帖、评论、检索和审核闭环 |
| M2 | Python / FastAPI 资料站、修订、引用、导入、论坛关联 | 内容贡献与版本管理闭环 |
| M3 | Java / Spring Boot 商城、Rust / Axum 资源、React / Next.js | 积分兑换、权益与内容实际使用；覆盖四种后端和两种 Web 栈 |
| M4 | Flutter 移动端与 Taro 小程序 | 在可用目标设备上完成各端承诺流程 |
| M5 | 桌面端、完整恢复演练、工程深化 | 安装、升级、备份恢复与运行证据 |
| 后续专题 | AI 检索、实时通信、图谱、Kubernetes 等 | 每个专题有场景、指标和采纳或归档结论 |

## 3. 外部集成验证

| 编号 | 验证 | 当前前置 |
| --- | --- | --- |
| INT-01 | 空 main 与 M0 分支实际推送，PR 目标与范围正确 | 用户明确 push 和 PR 授权 |
| INT-02 | GitHub 上 `repository-quality` 成功，最终 PR＋检查 ruleset 回读正确 | INT-01 及首次真实 CI 结果 |
| INT-03 | M0 通过 squash 合入 main | 检查成功、反馈收敛与用户合并授权 |
| INT-04 | 在线 GitBook Space 能按目录阅读 | 可选；账号、Space 和 App 授权 |

本地文档阶段交付与外部集成分别记账，不因等待授权而暂停无依赖工作，也不把外部未执行项标成通过。

## 4. 后续产品验收原则

每条核心需求包含前提、正常路径、权限、失败和恢复。交易额外覆盖并发与幂等；多端记录实际版本和设备；性能记录数据量、资源、负载及错误口径；备份必须恢复验证。

只有实际代码、对应运行证据与必要文档同时具备，才能确认产品能力交付。框架选型或文档通过不能替代业务验收。

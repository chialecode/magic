# 开源框架缺陷记录与反馈

记录第三方问题是 Magic 的正式学习目标。目标是积累可复现证据、理解边界、减少重复排查，并在获得授权后帮助上游修复；不以发现 bug 的数量衡量学习成绩。

## 1. 分类与事实

| 分类 | 含义 | 要求 |
| --- | --- | --- |
| suspected | 尚未排除误用、配置、环境或本项目缺陷 | 保留精确版本、现象和调查结论，不称为已确认框架 bug |
| usage-error | 用法或配置不符合官方契约 | 修正 Magic，记录容易误解的知识点 |
| documentation-gap | 行为与文档不一致或说明不足 | 区分实现错误和文档改进，提供官方引用 |
| confirmed | 最小复现足以证明违反契约，或上游明确确认 | 写明确认依据及受影响版本；本地确认与上游确认分开标记 |
| duplicate | 已有同一上游问题 | 链接原问题，不重复提交 |

分类描述原因，处理状态另用 `investigating / mitigated / reported / fixed-upstream / verified / closed`。上游合并修复、发布修复版本和 Magic 验证通过是不同事件。

## 2. 最小复现

1. 记录操作系统类别、运行时、框架及直接相关依赖版本、配置、输入、预期、实际和错误输出；脱敏后才入库。
2. 核对官方文档和支持范围，排除本项目业务代码、缓存、错误配置或不兼容版本。
3. 在独立合成项目中复现，尽量仅保留触发问题的依赖与步骤；固定版本和样本，写清命令。
4. 如有必要比较前后相邻版本和干净环境，说明最小触发条件与不能复现的环境。
5. 检索已有上游 Issue、讨论和修复记录，保存准确链接及日期，不能把相似标题当作同一问题。

复现工程放入 `experiments/upstream/<id>/`，实际有复现后再创建，不能用空项目伪装证据。文档记录放入 `docs/upstream/` 并登记；大型输入使用可重建的合成生成器。

## 3. 临时规避

优先采用已发布修复版本、明确配置或小范围适配器。确需补丁或 fork 时记录补丁来源、许可证、影响面、升级测试和退出条件，避免长期维护无来源的私有分支。

代码中的 workaround 引用 `UP-0001` 等稳定编号，限定受影响版本和触发条件。不能通过关闭权限检查、吞掉异常或放松数据约束规避框架问题。

## 4. 对外反馈

在本地完成英文或上游要求语言的 Issue／PR 草稿、最小复现和脱敏检查后，再请求用户授权发送。用户要求“记录 bug”本身不授权向上游发 Issue、评论、PR 或邮件。

疑似安全漏洞遵循上游安全政策与私密报告渠道，在明确授权和适当披露前不公开利用细节。未发送的草稿如实标记，不能构造上游链接或声称维护者已经确认。

## 5. 关闭与学习结论

上游发布后验证精确修复版本、最小复现和 Magic 相关回归；证实规避不再必要后删除，并记录关闭依据。若最终是使用问题，关闭缺陷但保留学习结论。

每条记录至少关联受影响功能、依赖版本、复现、分类、当前处理状态、临时规避、上游链接或未发送状态、回归测试和下一复核条件。周期性依赖升级时顺带复核，不自动向维护者反复催促。

# 开发流程与持续演进

## 1. 工作顺序

明确当前任务及权限 → 读取正本和实际状态 → 形成覆盖整个阶段的计划 → 连续实现与同步文档 → 自测与修复 → 自审 → 保存一个阶段提交 → 用户授权后 push／PR → 授权后合并与阶段整理。

计划是工作范围和验收依据，不要求每完成一个工作包都请求继续。用户新增需求时更新当前范围、设计和验收，不能只叠加聊天记录。

## 2. 技术学习驱动的需求

用 [技术提案](../templates/technology-proposal.md)记录业务场景、候选方案、实验指标和退出方式。正式引入前查官方文档、发行、许可证和维护证据；现成实现不满足要求时说明具体缺口，再决定自研范围。

实验与正式能力分开，结论允许是“不适合当前场景”。有价值的实验结果进入学习手册；未采纳代码按约定归档或删除，不能无期限占用正式部署资源。

## 3. 变更与文档同步

局部修复直接更新相关实现和说明；跨服务、数据语义或主框架变更使用变更提案与 ADR。需求、设计、协议、迁移、学习章节和验收受影响时同批同步。

Now／Next／Later 维护滚动范围；当前阶段只承诺已选入的需求。已确定约束的变化需要有效决定来源，不用技术偏好默默改变用户承诺。

## 4. 协作与待办

开发者可以自行完成计划、执行与自审；需要独立审查时交接分支、基点、当前提交、变更范围、检查和限制。只有明确要求时使用独立 Agent，不能把自审表述成第三方复核。

用户需要的决定、授权、外部配置和人工检查集中在 [USER-ACTIONS](../../USER-ACTIONS.md)，写明当前默认、具体动作和阻塞范围；非阻塞事项不暂停其他开发。上游 Issue／评论的公开发送属于独立外部动作，需要明确授权。

## 5. 阶段结束与清理

按 [质量门禁](quality-gates.md)验证并更新执行状态，记录失败、未执行和限制。完成一个文档设计不代表其产品功能实现；本地完成不代表远端已备份。

下一阶段开始时，将当前计划和报告中的有效结论提炼进正本，替换过期计划，历史通过 Git 查询。不无限追加流水式阶段总结，不删除仍需使用的本地配置或未归属的工作。

# 开发、部署与运行设计

状态：目标方案。M0 只有可执行的文档检查，本文的应用部署任务尚未实现。

## 1. 环境层次

| 环境 | 用途 | 约束 |
| --- | --- | --- |
| 文档环境 | 阅读、编辑、检查规范和学习内容 | 仅 Node.js / pnpm，无业务基础设施 |
| 开发环境 | 运行当前涉及的服务及其依赖 | Windows 可用 WSL2 / Docker Desktop，Linux 原生；按需启动 |
| Demo | 单机 Compose 演示业务闭环 | 合成数据、本地账号、固定版本，无真实支付或付费服务前置 |
| 未来运行环境 | 持续运营或 Kubernetes 专题 | 另行明确域名、资源、SLO、权限、发布与恢复策略 |

## 2. Compose 设计

按实际已实现服务组成部署，不预先放入四个不可用镜像。核心依赖包括入口、身份和领域数据库；资源、消息和完整监控按阶段引入。可选配置按能力组织，关闭可选监控不改变业务正确性。

镜像按提交或发行版本标记并记录 digest；初始化凭据随机生成，配置文件不提交秘密。公开入口仅暴露需要的端口，数据库、消息和存储管理界面留在私有网络。

容器分别有进程健康和依赖就绪检查。迁移使用受控一次性任务，并在启动新应用前完成；不能让多个应用副本并发争抢执行破坏性迁移。

## 3. 目标任务接口

后续实现 `task doctor`、`task dev`、`task check`、`task deploy ENV=demo`、`task smoke`、`task backup`、`task restore BACKUP=<path>`。当前唯一实际检查命令见 [质量门禁](../dev-rules/quality-gates.md)，不能运行本文任务证明部署成功。

部署应顺序完成环境检查、配置校验、镜像获取、依赖启动、迁移、可重复演示数据导入、应用就绪及核心冒烟；任一步失败返回非零退出和可定位信息。

重复部署不得重置数据、覆盖既有密钥或重复发放积分。卸载应用与删除持久数据分开，删除数据必须显式选择目标。

## 4. 备份与恢复

备份包含数据库、对象文件及恢复所需配置的安全副本；记录版本、校验和与一致性时间点。凭据不写入公开备份报告。

恢复使用隔离环境，依次恢复存储、数据库和兼容应用，核对资源引用、账号登录及积分账本。应用回滚仅在数据库仍兼容时成立，破坏性迁移需要数据库恢复方案。

首次形成可运行业务后定义可接受数据损失窗口和恢复时间，并实测。M0 不承诺未测量的 RPO／RTO。

## 5. 可观测性与故障

所有服务有结构化日志和关联请求 ID，基础指标包含流量、延迟、错误、数据库连接、队列积压和资源处理失败。日志不记录令牌、密码或完整个人内容。

OpenTelemetry 使用共同语义标记服务名与版本。下游超时、身份失效、队列延迟和磁盘不足分别有可理解的操作提示。告警只在对应能力实际运行后接入，避免创建永远无人处理的告警规则。

## 6. 发布链路

未来由 GitHub Actions 构建、GHCR 存储镜像、Release 记录版本清单，支持的环境通过 OIDC 使用短期凭据。部署和发布沿用明确用户授权，CI 不自动获得仓库设置或生产管理员权限。

当前 4 vCPU / 8 GiB / SSD 仅为后续基准测试建议，具体最低资源依赖实测。Kubernetes 通过独立学习需求验证其收益，不作为最初一键部署的前置。
